# 配置资产生命周期

状态：设计。本文提出应用、表单等可配置资产统一的草稿、发布、停用、归档规则；其中只有一部分已经实现，第 2 节列出当前代码的实际情况，其余章节都是目标规则，不代表现状。

适用范围：应用、应用菜单、业务表单。组件页面、流程定义等资产已有各自的版本机制，第 2 节一并说明，作为统一设计的参考。

当前实现的详细说明见[应用与应用菜单](../../architecture/low-code/applications.md)、[表单管理](../../architecture/low-code/forms.md)和[低代码平台](../../architecture/low-code/platform.md)；接口清单见 [API 参考](../../development/api-reference.md)；表单定义方式的参考见[业务表单定义参考](../../development/business-form-spec/README.md)。

## 1. 定位

应用和表单是产品资产，不是普通业务记录，不应该随时被覆盖或硬删除。生命周期模型要把以下操作区分清楚：

| 操作 | 含义 |
| --- | --- |
| 新建 | 创建一个草稿 |
| 保存 | 保存草稿或配置的修改 |
| 发布 | 让资产对最终用户生效 |
| 停用 | 停止运行期使用，保留配置和历史 |
| 删除或归档 | 删除只用于未被使用的草稿等安全情形；其他情形归档 |

## 2. 当前实现情况

### 2.1 应用

- `applications.status` 是自由字符串，代码中使用 `draft`、`published`、`disabled`，没有 `archived`，也没有版本表。应用属性的修改直接生效，不区分草稿和已发布内容。
- 运行期只认 `published`：`GET /applications` 只返回已发布应用，未发布或停用的应用对普通用户不可进入。
- 状态流转约束只在前端“应用与菜单”页面和 AI 工具（`applications.publish`、`disable`、`enable`、`delete`）中实现：只能发布草稿、停用已发布应用、启用已停用应用、删除草稿。`/admin/applications` 接口本身接受任意状态值、新建时默认 `published`，且允许删除任何状态的应用。
- 发布时没有完整性检查，只在新建和改编码时校验租户内编码唯一。
- 删除应用会一并删除菜单节点、菜单权限、表单绑定和角色绑定，不删除表单和业务数据。
- 应用和菜单节点用 `edit_token` 防止并发覆盖。

### 2.2 应用菜单

- `application_menu_nodes` 没有状态字段和版本，修改立即对运行期生效；只有 `visible` 控制是否显示。
- 运行期会过滤指向未发布表单或未发布组件页面的入口，所以表单停用后其菜单入口自动隐藏，但节点本身保留。
- 加入菜单时要求目标组件页面已发布。表单入口通过配置接口创建时不校验表单状态，由运行期过滤兜底；AI 工具 `menus.create_entry` 则要求表单已有发布版本。

### 2.3 业务表单

- `forms.status` 默认 `draft`。发布走 `POST /forms/{id}/publish`：先生成影响报告，有阻断项（新增必填字段缺数据、字段类型不兼容、必填字段缺失、枚举值收窄、控件配置错误）时返回 409；通过后写入 `form_versions` 不可变快照，并把表单状态置为 `published`。
- 草稿与运行期分离：运行期字段以最新发布快照为准，保存草稿不影响运行中的页面。已发布表单可以再次“发布更新”，产生新版本；也可以从任一已发布版本恢复草稿。
- 停用由前端调用 `PUT /forms/{id}` 把状态改为 `disabled`。停用后表单从应用菜单、个人工作台的表单目录中消失，非管理员无法进入以它为宿主的组件页面；但记录读写接口本身不检查表单状态，有权限的调用方仍可直接读写记录。重新启用等于再次发布。
- 删除只允许 `draft` 状态，且表单不能有任何应用绑定或菜单节点，否则返回 409。删除时 ORM 级联删除该表单在 `dynamic_records` 中的记录；如果表单使用物理表，物理表保留，不会被删除。
- 物理存储：`POST /forms` 新建表单默认使用物理表存储，建表与加列在新建表单、新增字段时立即执行，早于发布。归档字段只改元数据，保留物理列。
- 前端在保存后锁定字段编码和类型（`config.structureLocked`），已保存的表单编码不能修改。
- 没有 `archived` 的设置入口；`archived` 只在少数读取逻辑中被识别（例如前端把它显示为停用）。

### 2.4 其他已有版本机制的资产

| 资产 | 当前机制 |
| --- | --- |
| 组件页面 | `component_pages.draft` 保存草稿，`revision` 做并发检查；发布写入 `component_page_versions`，`published_version` 指向当前版本。没有停用和删除接口 |
| 流程定义 | `workflow_defs.status` 为 `draft` 或 `published`；每次保存递增 `version` 并写入 `workflow_def_versions` 快照，实例启动时固定版本。存在实例的定义不能删除 |
| 共享指标 | `analytics_shared_metrics` 保存草稿，发布写入 `analytics_shared_metric_versions` |
| 本体 | `ontology_versions` 与 `ontology_publish_logs` 记录发布 |

## 3. 状态模型（目标）

建议统一使用四个状态：

| 状态 | 含义 |
| --- | --- |
| `draft` | 可编辑的配置，尚未对最终用户生效 |
| `published` | 生效中的配置，在运行期界面可见 |
| `disabled` | 已发布资产暂停常规使用，历史和绑定都保留 |
| `archived` | 从常规管理流程中隐藏，仅为审计或恢复保留 |

如果产品暂时不需要，`archived` 可以后续再引入。

## 4. 新建

新建应用或表单应该得到草稿，而不是已发布资产：

```text
点击新建 → 创建本地或服务端草稿 → 编辑基本信息 → 保存草稿 → 准备好后发布
```

对表单，原设计要求“新建草稿不建物理表”。当前实现与此不同：新建物理表单时立即建表（见第 2.3 节）。如果要回到原设计，需要把建表推迟到发布，并相应调整新增字段的加列时机。

## 5. 保存

| 状态 | 保存行为 |
| --- | --- |
| `draft` | 保存草稿 |
| `published` | 视版本能力而定：保存为变更草稿，或直接保存非结构性配置 |
| `disabled` | 保存配置 |
| `archived` | 默认只读 |

第一阶段可以允许已发布资产直接保存低风险元数据，结构性修改仍需谨慎。

- 低风险：应用说明、图标、排序、置顶、负责人。
- 高风险：字段编码、存储列名、字段类型、是否允许为空、唯一约束、索引。

高风险修改应要求更强的确认，或走后续的版本与迁移流程。

## 6. 发布

发布把草稿投入运行期使用（`draft → published`）。

应用发布前应检查：

- 名称已填写。
- 编码已填写且租户内唯一（当前已实现）。
- 图标有效。
- 启动页面有效。
- 已配置可见角色，或明确声明对所有登录用户可见。

表单发布前应检查：

- 名称、编码已填写且唯一。
- 至少有一个字段（当前后端未强制；前端只在“应用与菜单”的发布按钮中检查，表单设计器的发布不检查）。
- 字段编码唯一，存储列名合法且唯一，字段类型受支持。
- 布局、动作、权限元数据有效。
- 修改已发布表单时，已了解对现有数据的影响（当前已由影响报告实现）。

## 7. 停用

停用让资产退出常规使用，同时保留配置和历史（`published → disabled`）。

应用停用：

- 默认从应用栏和工作台移除（当前已实现）。
- 保留应用配置、菜单结构、表单绑定和审计历史（当前已实现）。

表单停用：

- 默认禁止新增运行期数据（当前未在后端强制，见第 2.3 节）。
- 保留已有数据。
- 保留应用绑定，但在配置界面显示停用提示。
- 业务需要时允许只读查看历史数据。

## 8. 删除与归档

硬删除应当保守。

应用删除规则：

| 情形 | 处理 |
| --- | --- |
| 草稿，且没有运行期依赖 | 可以删除 |
| 已发布 | 不能直接硬删除 |
| 已停用 | 可以归档 |
| 存在菜单或表单绑定 | 需要先清理，或改为归档 |

表单删除规则：

| 情形 | 处理 |
| --- | --- |
| 草稿，无物理表、无应用绑定 | 可以删除 |
| 已发布 | 不能直接硬删除 |
| 已有业务记录或物理表 | 不能硬删除 |
| 被应用菜单使用 | 解除绑定前不能删除，或改为归档 |

表单硬删除不得静默删除业务表或数据。当前实现的差距：草稿表单删除时会级联删除其 JSON 记录，且不检查是否已有数据；物理表会遗留在数据库中，没有清理或归档流程。

## 9. 各状态的操作与按钮

| 状态 | 操作 |
| --- | --- |
| 草稿 | 保存草稿、发布、删除草稿 |
| 已发布 | 保存低风险修改、创建变更草稿（有版本能力时）、停用、复制为草稿 |
| 已停用 | 启用、归档、保存元数据 |
| 已归档 | 恢复（可选）、查看审计与历史 |

当前“应用与菜单”页面已按草稿、已发布、已停用三种状态显示“保存草稿 / 发布 / 删除草稿”“保存变更 / 复制为草稿 / 停用”“保存配置 / 启用”；表单在已发布状态额外提供“发布更新”。归档相关按钮尚未实现。

表单的高风险结构修改建议使用：

```text
[保存草稿] [查看数据库影响] [发布]
```

## 10. 表单存储影响

表单的生命周期规则比应用更严格，因为它影响运行期数据采集和已有记录。

发布前，界面应汇总存储与元数据影响：

- 新增的字段。
- 修改的字段。
- 删除或隐藏的字段。
- 校验规则的变化。
- 对已有记录的可能影响。

当前的发布影响报告已覆盖字段新增、类型兼容性、必填缺失、枚举收窄和归档字段仍有数据等情况，但还没有面向物理表的数据库影响评审。由于物理表在新建表单和新增字段时就已建表、加列，后续应补充一个独立的数据库影响评审，列出涉及的表、列、索引、约束、迁移步骤、回滚方式和数据保留策略。
