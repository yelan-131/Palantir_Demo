# 项目版本与发布规则

生效日期：2026-10-28。采用项目自定义的三段版本号，不称为严格 SemVer；历史编号不重排。

## 如何选版本

- 日常独立发布（功能、优化或修复）：末位加一，例如 0.3.18 → 0.3.19。
- 阶段升级：明确确认范围后，中间位加一、末位置零，例如 0.3.19 → 0.4.0。
- 大版本：明确确认稳定性、兼容性及迁移范围后，首位加一、其余归零，例如 0.4.0 → 1.0.0。不能仅因改动多就自动进入 1.0。
- 同一待发布批次继续维护原版本；已发布后有代码变更创建下一版本。
- 仅补充文档、测试结果或部署验收记录不升号；不得改写旧版本的功能范围或原发布日期。
- 用户明确指定版本或要求合并时优先遵循；涉及冻结历史的例外应注明原因、范围及日期，不静默覆盖。

## 状态与日期

- `draft`：待发布，可修改说明。`released_at=null`，`updated_at` 记录修改日期。
- `published`：发布内容冻结，`released_at` 为实际发布日期。部署和验收结果追加在对应说明中。
- 旧清单没有状态字段时，脚本按冻结历史处理。不根据标题或编写版本说明的动作猜测上线状态。
- 当前 0.3.18 保留已有记录，不由本次规则建设判定其部署是否完成。
- 发布前必须完成对应改动的构建、测试，确认数据库迁移和回滚安排；已知失败、未测范围要如实写明。部署后检查实际版本、健康状态及关键功能，再记录验收结果。

## 操作方式

统一使用 `scripts/bump_release.py`，同步根目录和后端发布清单、后端 APP_VERSION、前端 package/lock；另行维护 README、文档索引及 `release-X.Y.Z.md`。

新建日常版本示例：

```bash
backend/.venv/bin/python scripts/bump_release.py 0.3.19 --title '版本标题' --summary '范围说明' --added '新增内容'
```

阶段升级使用 `--kind minor`，大版本使用 `--kind major`；默认 `patch`。不允许回退、跳号、覆盖已发布版本，或跳过尚未发布的草稿。

同一草稿补充仍用该版本号；脚本替换该条目的标题和分类，调用时应传入该版本完整说明，避免只传增量而丢失既有内容。

正式冻结草稿示例（日期替换为实际日期，并传入完整说明）：

```bash
backend/.venv/bin/python scripts/bump_release.py 0.3.19 --status published --released-at 2026-10-29 --title '版本标题' --summary '范围说明' --added '新增内容'
```

脚本不部署服务器，也不证明测试已通过。`published` 由操作者依据实际发布证据设置，不能用来代替验收。

## 检查与约束边界

- 每次检查两个清单内容、前后端版本号、历史唯一性，以及新增范围和实际验证是否一致。
- 发布脚本测试：`cd backend && .venv/bin/python -m pytest tests/test_bump_release.py -q`。
- 脚本已约束正常升版入口；直接手改文件仍可绕过，当前没有仓库 CI 或分支保护强制拦截。代码评审应核对清单和版本说明；接入 CI 后再将一致性检查设为合并必需项。
