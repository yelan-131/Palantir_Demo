# 表单运行逻辑

更新日期：2026-11-17（对应代码版本 0.3.22 草稿）

本文面向产品、实施、测试和业务配置人员，从业务角度解释一张已发布的业务表单在运行时如何加载、如何保存和删除记录、权限如何判定、审批流程如何推进，以及记录保存在哪里。具体的配置操作见[业务表单配置指南](business-form-guide.md)，底层实现见[表单引擎](../../architecture/low-code/forms.md)，接口清单见 [API 参考](../../development/api-reference.md)。

## 1. 定位

业务表单不是一张写死的数据库表，也不是一个专门开发的页面，而是由表单元数据驱动的业务工作台。一张表单在运行时由以下几部分共同决定：

- 表单定义：名称、编码、状态和已发布版本。
- 字段：字段编码、类型、必填、默认值、选项来源、编码规则和计算规则。
- 展示：组件页面中业务列表的筛选方案、列表列、排序和工具栏。
- 权限：谁能看、能做哪些动作、能看和能改哪些字段、能看哪些记录。
- 流程：提交后进入哪个审批流程，每个节点由谁处理。

这些配置都先保存为草稿，发布后才对业务页面生效。业务人员看到的始终是最近一次发布的版本，不会被正在编辑的草稿影响。

## 2. 业务人员从哪里进入

业务人员通过应用菜单进入组件页面（`/pages/<页面编码>`），页面中的“业务列表”组件读取来源表单的记录。菜单只能挂载已发布的组件页面。

旧的表单直达入口 `/dynamic/<表单编码或 ID>` 仍然可用：数字按表单 ID 查找，其他值按表单编码查找。如果表单绑定了组件页面，入口会打开该页面；页面已启用但尚未发布时，会显示“此表单的页面尚未发布”；没有绑定页面时，使用内置的记录列表页。

非管理员访问时，服务端会依次检查：表单已发布、用户对表单有查看权限、用户的角色在页面允许访问的角色中（页面没有限制角色时不检查）。

## 3. 列表与查询

业务列表打开后，按以下顺序确定显示内容：

1. 启用了列表筛选时，先按当前用户匹配的筛选方案显示筛选区域。方案设置了必填筛选条件时，在填写并查询之前会提示“请先填写必填筛选条件并查询”，不加载记录。
2. 按“列表显示”中当前用户匹配的权限组确定可见列、默认排序和每页条数。
3. 向服务端请求一页记录，条件包括关键词、结构化筛选、排序和分页，每页最多 200 条。
4. 服务端只返回当前用户在数据范围内可以看到的记录，并去掉当前用户无权查看的字段。

页面上隐藏某个列或按钮只是为了界面清晰，真正的权限边界在服务端：即使绕过页面直接调用接口，也只能拿到有权限的数据。已删除的记录默认不出现在列表中。

导出使用与列表相同的筛选和排序条件，导出的是当前这一页的记录（文件名形如“页面名-第 N 页.csv”），而不是全部结果。导出时同样逐条检查记录和字段权限；为防止表格软件执行公式，以 `=`、`+`、`-`、`@` 等开头的单元格内容会加上前缀单引号。

## 4. 新增、编辑和删除

**新增。** 业务人员点击工具栏的“新增”或“填写申请”，表单按当前用户的字段权限显示可填写的字段。服务端保存前检查新增权限、字段是否允许当前用户填写，再计算默认值、编码、计算字段和填写规则，最后做数据校验（未定义字段、必填、类型、选项范围、唯一性、长度等）。每条记录都会记下保存时的表单版本号。

**编辑。** 编辑只提交修改过的字段，服务端把它们合并到原记录中，用合并后的完整数据做权限和校验检查，因此不会误删页面上没有显示的字段。正在审批中的记录受流程保护，不能直接修改。

**删除。** 删除需要删除权限，审批中的记录不能删除。删除是软删除：记录被打上删除时间，不再出现在列表中，但数据仍保留在库中，便于追溯审计。

**批量导入。** 支持 CSV 和 XLSX，单个文件不超过 5 MB、500 行、100 列。先预览并确认列映射，然后逐行按新增记录的规则校验和写入。导入需要同时具有导入和新增权限。

## 5. 权限如何判定

管理员不受表单权限限制。对其他用户，每次查看、新增、编辑、删除、导入、导出或审批，服务端都会按以下顺序判定，前一层得出结论后不再看后一层：

1. 角色权限：在“组织、身份与权限 → 角色管理”中为角色配置的表单授权。任一匹配的“拒绝”优先于“允许”。授权可以带条件规则（只对满足条件的记录生效）和字段规则。
2. 表单权限规则：在完整表单设计器的“权限设计”中按角色配置、随表单发布生效的规则。
3. 应用表单绑定：表单被直接挂到某个应用菜单、且用户属于该应用的角色时，按绑定允许的动作放行。挂载组件页面的菜单不会建立这种绑定。

三层都没有允许时，默认拒绝。没有任何角色的用户无法访问任何表单。

字段权限在表单权限之上再收窄。对每个字段，如果存在针对该字段的允许或拒绝规则，就按规则执行；如果所有字段都没有字段级的允许规则，那么只要表单级允许，用户就能访问全部字段，显式拒绝的字段除外。需要注意，一旦为某些字段配置了字段级允许，没有被允许的其他字段就会对该角色不可见。此外，“权限设计”中为某个角色设为不可见的字段，对属于该角色的用户不返回；标记为敏感的字段会按规则脱敏。

数据范围（全部数据、仅本人、本部门、本部门及下级等）决定用户能看到哪些记录。权限模型的完整说明见[权限模型](../../architecture/permissions.md)。

## 6. 草稿、提交与审批

表单没有配置审批流程时，业务人员“保存”后记录直接生效。

配置了审批流程时，记录有自己的申请状态，业务流程如下：

1. 业务人员新增时“保存草稿”，草稿允许暂时不填全部必填项。页面提示“先保存草稿，完成填写后从记录详情提交审批；驳回后可修改并重新提交。”
2. 填写完成后，在记录详情中“提交审批”。只有申请人或管理员可以提交，记录必须处于草稿或已驳回状态。提交时服务端按最新的填写规则重新检查一遍；如果规则变化导致数据需要调整，会提示“表单规则已更新，请重新保存草稿后提交”。
3. 提交时表单必须恰好对应一个已发布的审批流程，否则提示“此表单尚未配置审批流程”或“表单须配置唯一的审批流程”。提交成功后提示“已提交审批，可在流程与待办 → 我发起的追踪”。
4. 处理人在“流程与待办”的“待审批”中处理。审批时只能填写审批意见，不能修改业务字段；驳回必须填写意见。驳回后申请人可以修改并重新提交。
5. 处理时会核对待办所在的节点。如果流程已经推进到下一个节点，旧页面上的操作会被拒绝，需要刷新后重试。

流程在提交时根据字段值确定条件分支，并固定使用当时的流程定义版本，之后修改流程不会影响已经在途的申请。审批节点的字段可见性设置会影响记录在审批期间对各角色的可见内容。参与审批本身不会授予处理人查看来源表单其他记录的权限。

当前运行时不支持并行网关和汇聚网关，包含它们的流程无法发布；会签和或签通过同一节点的多个审批组实现。流程中的“自动任务”可以在流程经过时异步把数据下发到站内其他表单（创建草稿）、外部 API 或 Webhook，失败后可以在流程实例的下发记录中重试。

## 7. 发布与版本

每次发布表单都会生成一份版本快照，包括字段、布局、列表、权限和分析配置，配置了流程时还会一起发布流程定义和触发绑定。发布前服务端会结合现有业务数据做影响检查，例如新增必填字段而历史记录没有值、字段类型与历史值不兼容等情况会阻断发布。

业务页面始终读取最近一次发布的定义。需要回到某个旧版本时，可以把该版本“恢复到草稿”，检查后再发布为新版本；恢复不会改动线上页面和已有业务数据。组件页面有自己独立的版本和发布，与表单版本互不影响。

## 8. 记录存储在哪里

业务记录有两种存储方式，对业务人员的使用方式没有区别：

- 动态存储：记录以 JSON 保存在 `dynamic_records` 表的 `data` 字段中，按表单区分。
- 物理表存储：每张表单有自己的数据库表，新建表单的表名为 `t{租户 ID}_business_{表单编码}`（较早创建的表单可能沿用不带租户前缀的 `business_*` 表名），每个字段对应一列。新建表单时如果没有指定已有的数据表，服务端会自动生成表名并使用这种方式，所以从“业务数据”新建的表单都是物理表存储。

物理表和列在保存表单结构时就可能创建，不必等到发布。字段归档后，新的填写表单不再显示它，但数据库中的列和历史数据仍然保留。

## 9. 示例：设备告警处理单

以“设备告警处理单”为例，一条记录的完整生命周期如下：

1. 发起人从应用菜单进入告警页面，用筛选方案按“严重”等级和发生时间查找记录，点击“填写申请”新建一条告警，告警编号按编码规则自动生成，保存为草稿。
2. 补全设备、责任人和附件后，在记录详情中“提交审批”，记录进入“处理人处理”节点。
3. 处理人在“流程与待办”中收到待办，查看记录后填写审批意见并通过，流程进入“主管审核”。
4. 主管审核通过后流程结束。如果主管驳回，发起人可以修改记录并重新提交。
5. 整个过程中，每个角色只能看到权限允许的记录和字段；任何删除都是软删除，记录可以追溯。

## 10. 当前边界

以下内容目前不能作为现有功能对外描述：

- 并行网关、包容网关、定时事件、脚本任务和子流程的运行（未实现）。
- 审批节点内修改业务字段（未实现）。
- 一次导出全部查询结果（当前只导出当前页）。
- 回滚物理表结构；版本恢复只恢复配置，不删除已经创建的列。

现有的请求内缓存和批量读取优化，不代表已经验证过生产规模的容量；大数据量下的索引、归档和长期性能需要专门评估。
